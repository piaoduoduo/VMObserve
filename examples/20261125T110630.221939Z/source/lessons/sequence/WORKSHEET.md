# 课内 3.2：连续三次 malloc 与系统调用

依据当期 `lab3_2/malloc.c` 的顺序，在同一进程中申请 1 KiB、256 KiB、1 MiB，三个块同时存活，再全部释放。观察点由人工暂停改为自动保存完整 smaps。这个课例不写入用户数据；逐页写入与缺页处理在按需调页课例中观察。

## 先预测

1. malloc 是 C 库接口。连续调用三次，是否一定出现三次内核内存管理调用？
2. 三个返回地址一定分别位于三个映射中吗？
3. free 完成后，原地址范围的映射是否一定消失？

## 实际运行

Windows 项目根目录执行 `./work/vm.ps1 retest --suite sequence`，复用 openEuler 虚拟机。
Linux 执行 `python3 work/run_all.py --suite sequence`。默认重复三次，每次是一个新的进程。
网页切换到“连续 malloc 与调用”，点击“运行连续 malloc 与跟踪”。选择历史记录仅回放。

每次保存五个阶段：申请前、第一块申请后、第二块申请后、第三块申请后、全部释放后。
`stdout.jsonl` 保存同一 PID、返回地址和 program break；`smaps.stderr.txt` 保存各阶段完整映射；`syscalls.txt` 保存调用参数、返回值与动作标记。`build/strace.stdout.log` 保存跟踪工具版本。

## 用证据作答

先看表中的原始行号：只比较 ACTION BEGIN / END 内的 brk、mmap、munmap、mremap。启动时的动态库映射以及采样自己的调用不能算进 malloc。

再比对返回地址。只有该块范围落在本步新取得的 brk / mmap 范围内时，才确认这种地址对应关系。没有内存管理调用是可确认的观测；分配器复用了哪个内部空闲块，当前没有内部跟踪证据。

最后比较映射。两个块可以共用或合并到一个 VMA；相关映射的 Size / RSS 每段只统计一次，仍包含管理信息和同区其他对象。释放后保留的映射不等于泄漏，已释放的指针不能读写。

记录你的解释，并注明对应运行 ID、案例 ID、原始行号。把“本次看到的现象”和“所有 malloc 都会这样”的断言分开。跟踪缺失或动作标记不完整时，这一轮证据不足，应修复环境后重新采集，不能用历史结果补齐。
