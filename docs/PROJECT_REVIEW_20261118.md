## 最能代表作品的课例

**程序申请了三块内存，为什么只有两段相关映射，而且只驻留了 16 KiB？** 建议用这个问题开场，让学生先猜，再打开证据。

已复读 openEuler 历史 `20261116T090129.522833Z` 的 `sequence-1`：1、256、1024 KiB 三块同时存活，合计申请 1281 KiB；相关的整段虚拟映射去重后为 2 段，共 1428 KiB，整段驻留合计 16 KiB。后两块落在同一段，不能把该段 RSS 对两个对象各加一次。`syscalls.txt` 第 20、31、42 行分别是扩堆和两次映射，第 54、55 行是两次解除映射。申请量、映射量和驻留量回答三个不同的问题；这一次的调用组合不是所有 malloc 的规律，也不能充当「某次 malloc 没有内存管理系统调用」的反例。

[C 探针](../work/proj5-course/group3_sequence.c)标出动作边界，[Python 解析器](../work/vmobserve/sequence.py)检查调用所在区间、返回地址是否被映射完整覆盖，以及不同块是否共用映射，再让前端指回原文。[COW/THP 诊断](../work/vmobserve/diagnosis.py)也有值得保留的判断：共享计账不能直接当逐物理页复制，大页请求成功也不等于真正观察到了大页。这里是项目的技术贡献。

## 审美、架构、课程与参赛材料

- **视觉。** 白底、深青、选中状态和历史标签适合投影，建议保留。桌面首屏最醒目的是「运行完整实验」、八个并列标签和以系统名称开头的历史行。在 1280×850 的有数据页面中，第一张观测表刚出现在画面底部；390×844 窄屏先要经过历史卡片和横向主题。首页改成「一句课堂问题 → 一条真实结果 → 查看原始证据」，重新运行作为第二个动作。历史行先写实验名，再写系统和时间；完整课内目录留给验收。
- **代码。** 保留 C + Python 标准库 + 本地网页，暂无必要更换框架。维护痛点已有实例：后端知道有哪些原件，前端却硬编码文件类型；复验目标和界面用语也分开维护。先统一案例类型、证据清单和环境关系，然后只拆改到的主题渲染函数。
- **教学。** 主线沿虚拟地址/映射、驻留/缺页、共享/复制展开，学生应能写预测、找到原文、修改解释。保留 fork 到 COW 的衔接，其他课程工具归入扩展。现有[连续 malloc 任务单](../work/lessons/sequence/WORKSHEET.md)已能承载一次试用；尚需留存真实学习者的回答和卡点，自动演练不能充当试用。
- **往届对照。** [RRAM](https://github.com/oscomp/first-prize-osf2024-RRAM)的强项是从模拟器、运行时、虚存实现到用户程序贯通。我们的优势方向是让一个学生能从真实 Linux 记录解释机制。可借鉴它把不同层证据讲成一条线的方式，不必追同样的系统规模。其他项目见[已有原始资料对照](NATIONAL_REFERENCE_STUDY_20261116.md)。本次查 1037.wiki 未取得可核实的同课报告正文，没有将搜索摘要当证据。
- **交付。** 主 README 前部说明连续 malloc 已完成，后部仍列待完成；顶部第 1/2 组文档链接在所审提交中还不是已跟踪文件。明确分出首次使用、已有实测、尚待验收，并核对[队伍记录的许可证待办](COMPETITION_COMMITMENTS.md)。

1. 用上表的触发条件修正环境来源、复验条件、笔记案例绑定和通用原件入口；验收看导出后的证据能否找回。

3. 请一位未参与实现的人独立操作：先预测，找出哪两个块共用一段，再用证据解释 16 KiB 的含义。保留原回答、修改后的解释和一个操作卡点。一份试用只能说明这一名使用者的情况。做完这三步后，再决定要不要加新实验。
