## 真正读到的代码和报告说明了什么

### 1. OS-Barrier：题目很小，但学生任务是明确的

固定快照：`f48439e37e326efd6ab2484db36f29419675bc1c`。阅读范围是三个文本文件全文。

它围绕带超时的线程屏障设计实验。README 交代本校课程中缺少多线程实践的问题，再解释实验步骤、运行环境、参数、观测与改进。学生版留出四类任务：判断是否跳过本轮、更新时间和轮次、等待并处理超时、最后一个线程唤醒其他线程。参考实现以 pthread 互斥锁和条件变量组织 20 轮执行。

值得借鉴的是“学生需要写什么”与“完成后观察什么”直接对应。咱们目前的六步课程页已经有问题和解释，但主要引导看现成程序结果，还没有独立成套的学生任务、参考解与评判依据。

参考实现也不能照单全收。静态阅读发现 `barrier.c:51` 在加锁前读取共享轮次，而轮次在锁内更新；条件等待调用附近没有按轮次条件循环复查。它值得进一步做并发正确性验证，不能凭示例输出就认定稳健。本次没有运行该程序，也不据这些问题推断实际获奖评分。

定位：[设计/教学文档](https://github.com/HarvestMoons/OS-Barrier/blob/f48439e37e326efd6ab2484db36f29419675bc1c/README.md)、[学生代码](https://github.com/HarvestMoons/OS-Barrier/blob/f48439e37e326efd6ab2484db36f29419675bc1c/barrier_empty.c)、[参考实现](https://github.com/HarvestMoons/OS-Barrier/blob/f48439e37e326efd6ab2484db36f29419675bc1c/barrier.c)。

### 2. BirdOS：可借鉴的是原理、代码、测试互相对应

固定快照：`ee9a29688179724783ed2373d04e7df11ff5e610`，最后提交时间为 2026-09-16，晚于其自述的 2024 届比赛。**当前仓库不能直接视为当年的最终参赛版本。** 作者描述中的总代码量和名次没有独立核验，也不作为比较指标。

本次阅读 `docs/document/内存管理.md` 第 1–694 行，重点看 COW 与懒分配；随后核对 `kernel/mm/vm.c:319–392` 和完整 `user/test/cowtest.c`。

具体看到：`uvmcopy` 对原可写页清除写权限、设置 COW 标志、共享物理页并增加引用计数；`copyout` 也检查 COW 并调用分配处理。报告不仅解释 fork，还把测试分成共享条件下的 fork、三进程写入、内核向用户缓冲区写数据等情况。测试程序与报告中列出的函数对应。

对咱们的启发是：COW 的“为什么”需要能追到页表写权限、写保护异常、复制或重新变为可写的处理过程；测试也应覆盖会推翻简单解释的条件。VMObserve 当前证明的是计账变化和父子值隔离，尚不观察逐页复制事件。两种作品任务不同，**没有理由因此要求本题重写整套内核**。可先补原理与源码阅读说明，若确有无法区分的假说，再有针对性增加观测。

其测试通过截图、性能好处叙述属于作者材料，本次没有编译或运行 BirdOS，也没有测得其性能。

定位：[内存设计文档](https://github.com/laojiahuo2003/bird-OS/blob/ee9a29688179724783ed2373d04e7df11ff5e610/docs/document/%E5%86%85%E5%AD%98%E7%AE%A1%E7%90%86.md)、[页表代码](https://github.com/laojiahuo2003/bird-OS/blob/ee9a29688179724783ed2373d04e7df11ff5e610/kernel/mm/vm.c#L319)、[COW 测试](https://github.com/laojiahuo2003/bird-OS/blob/ee9a29688179724783ed2373d04e7df11ff5e610/user/test/cowtest.c)。

## GitHub 同类工具：哪些能力已经常见

### smem：RSS/PSS 统计本身不是我们的独创

读取的是 [kwkroeger/smem](https://github.com/kwkroeger/smem) 的 Python 3 改编版，快照 `1910834fbad7809507fc23406de0a17c6bb148dc`，不是声称读了全部 smem 上游版本。

实际读到 `pidmaps` 从 smaps 解析映射与 kB 字段，`pidtotals` 聚合 RSS/PSS 并按私有干净页加私有脏页计算 USS；进程汇总入口可选择 smaps_rollup。它提供进程、映射和用户等统计视角。因此不能把“读 smaps、显示 PSS”本身当作特色。

还发现此快照虽然声明 `--source` 参数，但所读 `main` 仍创建固定 `/proc` 数据源，没有看到该选项连接到离线源。因此本次没有按参数名称宣称它已支持离线回放；也没有声称这代表其他 smem 版本。

**本次新增历史数据交叉核对：**提取该快照未改动的 `pidmaps` 函数，将咱们两环境 v0.3 的课程 smaps 原文交给它解析。按同一申请地址范围选取重叠的整个 VMA，比较 Size、RSS、PSS、私有脏页、共享脏页、AnonHugePages、Swap 七项。

- 24 个历史课程案例 × 每例 6 阶段 = **144 个快照**。
- **1008 个字段比较全部一致，0 项差异**。
- 这是历史原文的解析一致性核查。不是新执行 144 次实验，不是 smem 整个应用的验收，不证明采样没有扰动、对象范围精确、根因正确或教学效果。
- 两个解析器共享同一批原始证据和地址选择口径，因此还不能替代独立采集。

脚本与完整结果：`output/research/regional-course-20261111/crosscheck_smem.py`、`smem-crosscheck.json`；结果保存输入文件哈希。本次未修改这些历史输入。

### memory-watcher：记录、回放和图表也已有实现

读取 [Karry/memory-watcher](https://github.com/Karry/memory-watcher)，快照 `d5a72cd95a09490d71b4a17e2ce894d4a071b66d`。实际读 README、采集实现、映射类型、数据库建表以及回放主流程。

`ProcessMemoryWatcher::readSmaps` 解析映射的 RSS/PSS；`Storage` 保存进程身份、地址范围和带时间的观测；`Replay::run/step` 按记录时间读取并展示数据，还处理 PID 重用时的身份歧义。README 另外展示历史曲线。没有在本机编译 Qt 程序，曲线效果尚未实测。

因此咱们的历史回放、导出和页面是有用的工程能力，但不能单独作为创新论据。咱们可争取的差异是：**围绕一个课内疑问，把具体程序动作、可核查观测、解释成立的条件和下一次对照接起来。** 这仍需要真实案例和用户试用来证明价值。

## 以冲一等奖为目标的内部完成标准

下面是基于当期题目和本次对照提出的工程目标，**不是官方分数线，也不保证获奖**。本题允许聚焦一个机制方向，不需要为了参考作品的模块数量扩成整套 OS。

1. **做成三节可使用的实验课。** 每节都有课内知识定位、操作前预测、学生要完成的任务、真实运行、原始证据、解释与变式。先做完整一节，再复用结构。学生任务可以是修改访问方式、选择观测口径或设计对照，无需都做复杂内核填空。
2. **每节至少讲透一个容易误判的现象。** 按需分配：小块首次写未新增缺页、free 后映射保留；COW：RSS 合计增加不等于立即复制同量内存；THP：请求成功不保证采样时有大页。前两类已有真实素材；第三类的不生效样本仍待实际采集。合计“三个主问题及三个反例”是内部内容目标，不是比赛数量要求。
3. **完成一条可信的诊断与复验全过程。** 列出候选解释及证据缺口，安全地改变一个条件，生成新记录，再评价原解释。受控设置导致的 THP 抑制要明说是人为条件；无法区分的原因继续保留未知。不要求无依据地追求 100% 自动诊断。
4. **证明工具的新增价值。** 同一个问题先用原课例/手工 smaps 或 smem 完成，再用本工具完成。记录能否定位到动作、是否误把 RSS 相加当复制量、是否把 THP 建议当结果。暂不宣称速度或理解率提升；需要实际对比之后再写结论。
5. **让其他人能使用并留下反馈。** 先由用户边复习边亲自完成一节，再进行真实使用者试用；记录安装失败、解释看不懂、回答与修改。小样本只作可用性和问题发现证据，不包装成普遍教学成效。没有官方规定必须找几人，也不以招募队友为前置条件。
6. **形成能复核的交付。** 独立目录/干净环境复现、关键失败与恢复、源码和原始证据可追溯；正式报告围绕课程痛点、已有方法不足、设计取舍、实验证据和限制组织；视频展示一个完整问题和复验。AI 记录保持真实，用户应能解释与修改自己的关键实验。

最值得优先补的技术深度：真实 THP 不生效的条件排查，或 malloc 的 brk/mmap 系统调用证据。是否引入跟踪工具，应由具体问题决定；PFN/eBPF、更多系统/架构、大模型和新增漂亮图表都不是当前必选项。
